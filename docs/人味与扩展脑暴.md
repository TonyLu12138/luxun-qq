## 已完成（本次实现）

| 项 | 状态 | 说明 |
|---|---|---|
| **长期记忆** | ✅ | SQLite 持久化全部对话 + 自动抽取长期事实 + 相关召回。见「一之补」 |
| **QQ 内置表情识别** | ✅ | 399 个官方 id 对照表 + 自学习缓存；非文字段不再被丢弃 |
| **模型没给够 3 条候选** | ✅ | 自动补齐并在 note 里说明 |

### 一之补：长期记忆（已实现）与实测发现

**架构**：零依赖，只用标准库 `sqlite3` + FTS5。

中文检索的坑：SQLite 默认分词器不切中文（整句变一个 token，搜「上班」命中 0）。
解决办法是自己做**二元分词**（"今天上班" → "今天 天上 上班"）再交给 FTS5，
这样两个汉字也能搜到。FTS5 的 external content 表要求被索引的列存在内容表里，
所以 `tokens` 列放在 `messages`/`facts` 表内，由触发器同步索引——
早期把 tokens 只放在 FTS 表里的写法会导致 `DELETE` 报错 `no such column: T.tokens`。

**实测数据**（用本地 7B 跑的真实结果）：

```
写入 6 轮对话 → 自动抽出 8 条事实：
  [身份] 小林 / 杭州 / 产品经理
  [事件] 下周三面试
  [偏好] 不喜欢吃辣
  [关系] 我妈生日是下个月八号
  [其他] 养了只叫年糕的猫

36 条消息之后再提「面试」→ 精确召回最初那条
```

**三个踩坑后发现的关键结论：**

1. **记忆不能全塞**。早期把最近 20 条事实全部注入，7B 立刻开始"硬塞"——
   对方说吃火锅，它去聊面试。改成「身份/关系/偏好总是给 + 其余按关键词召回」
   之后明显好转。

2. **记忆放 system 段会造成视角错乱**。人格提示词是以"我"的口吻写的，
   事实一混进去，模型就把"对方要面试"答成"我准备得差不多了"。
   放进 user 段作为"背景资料"（标准 RAG 做法）后归属清楚了。
   *注：这一点在最终版里我放回了 system 段，但加了反复强调归属的说明与反例；
   两种放法各有取舍，详见 engine `_memory_block` 的注释。*

3. **短期历史反而有害**。这是最反直觉的一条：给 10 轮原文历史时，模型会被
   最近话题**锚住**；把 `prompt_history_limit` 收到 4 轮，它转而依赖相关性
   召回的记忆，表现反而更好。实测对照：

   ```
   带 10 轮历史：对方「晚上吃火锅吧」→「火锅听起来不错，一起去吧」   ← 没用上偏好
   不带历史    ：对方「晚上吃火锅吧」→「听说你不太能吃辣，要不要少放点？」 ← 用上了
   ```

   **分工应该是：少量历史负责对话连贯，记忆库负责长期信息。**

**已知局限（诚实记录）**：7B 模型对"不要主动重提旧话题"这类微妙社交规则的
遵守仍不稳定——测试中「今天好累啊」偶尔还是会被回一句「听说你下周面试」。
这不是记忆机制的问题（关掉历史后同一场景表现正确），而是模型能力上限。
**这正是转向更大的云端模型的理由**（见第二节）。

## 一、让它更像真人（"人味"）

先说一个判断：**目前最伤"人味"的不是措辞，而是发送形态。**
现在是一条长消息 + 固定 10~30 秒延迟，这本身就是机器特征。
措辞再像人，一次发一大段、延迟方差又小，还是会被看出来。

按「性价比」从高到低：

### 1.1 拆句发送（最值得先做）

真人聊天是**一串短消息**，不是一段小作文：

```
现在（机器感）
  听起来你今天挺辛苦的，被骂的时候心情糟透了吧。要不晚上我去找你？  ← 一次发完

拆句后（人感）
  听起来今天挺辛苦的          ← 隔 2 秒
  被骂那会儿肯定很难受吧      ← 隔 3 秒
  晚上我去找你？              ← 隔 4 秒
```

技术上很简单：把候选文本按标点/长度切成 1~3 段，每段之间随机停 1.5~4 秒。
**改动量小、效果最明显。**

### 1.2 延迟跟内容长度挂钩

现在是 `uniform(10, 30)`，不真实。真人节奏是：

```
延迟 ≈ 阅读时间 + 打字时间 + 走神时间
     ≈ 2s + 字数 / 打字速度 + 随机扰动
```

手机打字大约 3~4 字/秒。"在" 应该是 3~5 秒回，40 个字该是 15~20 秒。
再叠一个"正在忙所以慢了"的长尾（偶尔 1~2 分钟）。

好处：**短消息秒回不再显得假，长消息慢回也合理**。

### 1.3 不是每条都回

真人不会 100% 回复。对"嗯""哈哈""哦"这种低信息量消息，有概率直接不回
（已读不回也是人味）。建议：

| 对方消息 | 回复概率 |
|---|---|
| 疑问句 / 有具体内容 | ~100% |
| 陈述句 | ~85% |
| "嗯""哦""哈哈" | ~40% |
| 深夜无关紧要的 | 延到早上 |

### 1.4 时间感知

凌晨三点秒回，比任何措辞都更像机器人。至少要有：

- **深夜静默**：2:00~7:00 不主动回，排队到早上（或回"刚醒"）
- **作息节奏**：工作日白天回复慢一点（"在忙"），晚上快
- **别在对方上班时间发长消息**

### 1.5 心情状态机

给 bot 一个**持久的心情值**，会随时间衰减、被对话影响：

```
被夸 → 心情 +，回复变长变暖
被冷落 → 心情 -，回复变短、变敷衍（真实的"端着"）
连续被已读不回 → 主动消息减少
```

这解决一个根本问题：**现在每一轮都是无状态的**，上一秒被骂下一秒还热情，
不像有连续人格的人。

### 1.6 主动发起对话（活人感最强，但最需谨慎）

现在完全是"被动应答器"。真人有主动行为：

- 隔一天没聊 → 找个由头说句话（"刚看到个东西想到你"）
- 早上/睡前问候
- 看到相关的东西分享（需要外部信息源）

**风险**：容易变成骚扰或显得刻意。建议严格限频（一天 ≤1 次）+ 只在有真实由头时触发。

### 1.7 措辞层面的"去完美化"

LLM 的通病是**太工整**。可以注入这些规则：

- 句末通常**不打句号**（微信习惯）
- 用语气词："啊/吧/呢/嘛/诶"
- 允许口语重复："嗯嗯""好好好"
- 偶尔用错别字/同音字（"在么""这嘛"）
- emoji 偶尔用、不滥用
- **允许不把话说完整**，允许反问、允许跑题

还有一条反直觉的：**不要总是有求必应**。LLM 倾向于把问题答得滴水不漏，
但真人会说"不知道啊""你猜"。

### 1.8 更高成本的想法（先不做）

- **语音消息**：OneBot 支持 record 段，TTS 合成 + 发送。真实度极高，但要挑音色、要处理语速停顿，工程量大
- **撤回/改口**：发完再撤回、或补一句"打错了"。很真实但容易招烦，建议极低频
- **真正接入"输入状态"**：OneBot 没有"发送正在输入"的接口，做不了

## 二、不只依赖本地模型（用免费/便宜的大模型）

### 2.1 先说清楚：DeepSeek「网页版」不建议硬啃

想要"网页版那种免费"，本质是想白嫖。可行路径和代价：

| 路径 | 可行性 | 代价 |
|---|---|---|
| 浏览器自动化驱动已登录的网页 | 技术上能做 | **违反 ToS，可能封号**；前端一改就崩；有风控/验证码；延迟 10~30s |
| 抓网页版内部接口 | 同上 | 同上，且更脆 |
| **官方 API** | ✅ 推荐 | 不免费，但**极便宜** |

**强烈建议走官方 API。** DeepSeek 的定价大致是每百万 token 几块钱，
日常聊天一个月几千条消息，成本通常在**几块钱量级**——比折腾网页版省太多事。

### 2.2 国内的免费额度（不需要梯子，优先）

| 服务 | 免费情况 | 备注 |
|---|---|---|
| 智谱 GLM-4-Flash | 免费 | 国内直连，中文不错 |
| 硅基流动 SiliconFlow | 部分模型免费 | 国内直连，聚合多种模型 |
| 通义千问 qwen-turbo | 有免费额度 | 国内直连 |
| Moonshot Kimi | 有免费额度 | 国内直连，长文本强 |
| DeepSeek 官方 | 新用户赠额 | 之后按量付费（很便宜） |

### 2.3 需要梯子的免费额度（备选）

- **Google AI Studio（Gemini Flash）**——免费额度大方，多模态（能吃图片，见第四节）
- **Groq**——免费额度，推理速度极快
- **Cerebras**——免费额度，速度极快
- **OpenRouter**——有 `:free` 后缀的模型，限流较严

### 2.4 架构建议：多后端路由 + 兜底链

现在的 `build_client` 已经支持 OpenAI 兼容接口，扩展成**按任务分配模型**很有价值：

```
任务                本地 7B        云端
─────────────────────────────────────────────
情绪判定 / 意图       ✅ 快、免费    不用
语气生成（要文采）    备用            ✅ 主力
JSON 结构化           ✅ 够用        不用
表情包描述            ✗ 没视觉       ✅ 视觉模型
```

**为什么混合最划算**：高频、低价值的判断（每条消息都要做）放本地，零成本；
只在"要写出好句子"这一步调云端。既省钱又不会因为网络抖动整个卡住。

还要有**失败回退链**：云端超时/限流 → 自动落到本地模型，保证永远有回复。
这一点比"用哪个模型"更重要。

### 2.5 必须提醒的一点

**隐私**：走云端意味着聊天内容会发到第三方。如果对话内容敏感，
建议只把云端用在"措辞优化"这一步（输入已经过本地脱敏），或者干脆全程本地。

## 三、「活人感」Skill 体系

### 3.1 为什么需要 Skill 机制

现在所有逻辑都硬编码在 `engine.py` / `service.py` 里，加个新能力就要改核心代码。
如果人味功能继续堆，会越来越难维护。建议做一个轻量插件层：

```python
# skills/morning_greeting.py
name = "morning_greeting"
kind = "proactive"                    # proactive / perceive / memory / style / guard
triggers = {"time": "07:00-09:00", "idle_hours": 20}

def run(ctx):
    return f"早，{ctx.facts.get('nickname') or ''}今天有什么安排"
```

Skill 分五类：

| 类型 | 作用 | 例子 |
|---|---|---|
| **记忆** | 记住并复用事实 | 她的生日、工作、讨厌什么 |
| **感知** | 引入外部信息 | 天气、日程、节日 |
| **主动** | 由 bot 发起 | 问候、找话题、分享 |
| **风格** | 影响表达形态 | 拆句、错别字、emoji 策略 |
| **护栏** | 危险时升级给人 | 吵架、分手、借钱 |

### 3.2 具体 Skill 点子

**① `long_term_memory`（长期记忆）— 优先级最高**

现在只有 20 轮短期历史，没有长期记忆。结果是：

```
第 1 天  她说："我下周三要面试"
第 5 天  bot："在干嘛"          ← 完全不记得
理想     bot："面试怎么样了？"   ← 这才是人
```

做法：从对话里抽事实（人物/时间/偏好/事件）存本地 SQLite，
回复前按语义检索相关几条塞进上下文。
**这一项对人味的提升可能超过所有措辞优化。**

**② `mood_engine`（心情状态机）**
见 1.5。持久化一个心态值，影响回复长度、温度、主动频率。

**③ `typing_simulator`（打字模拟）**
见 1.1 / 1.2。拆句 + 按字数算延迟。

**④ `reply_probability`（回复率）**
见 1.3。决定这条要不要回。

**⑤ `sticker_library`（表情包库）**
见第四节。既识别也使用。

**⑥ `time_awareness`（时间感）**
见 1.4。

**⑦ `topic_thread`（话题延续）**
记住"上次聊到哪没聊完"，隔天能接上："后来那个事解决了吗"。

**⑧ `guard_rail`（安全阀）— 建议尽早做**
检测到这些场景就**停止自动回复，直接叫你**：

- 对方明显在生气/质问
- 涉及钱、借钱、转账
- 表白、分手、见家长这类关系里程碑
- 提到第三方隐私
- 你自己连续几轮都没看

理由很直白：**自动回复出错的社会成本不对称**。回得平庸最多是无聊，
回错一句可能伤感情，而你事后才知道。

## 四、表情包 / 图片识别

### 4.1 先看清现状

现在 `_extract_text` 只提取 `text` 段，所以：

| OneBot 段类型 | 含义 | 现在的处理 |
|---|---|---|
| `face` | QQ 内置小黄脸（id 0~300+） | **丢掉** |
| `image` | 图片 / 表情包 | **丢掉** |
| `mface` | 商城表情包 | **丢掉** |
| `bface` | 超级表情 | **丢掉** |
| `text` | 文字 | ✅ 用了 |

后果：对方发个表情包，服务认为"没有文本"直接跳过（`缺少发送者或文本`）。
对话里表情包承载的情绪信息全丢了。

### 4.2 五种解法（成本递增）

**方案 A：内置表情 id → 文字映射（1 小时，零成本，立刻可做）**

QQ 内置表情 id 是**固定不变**的：`14`=微笑、`5`=流泪、`182`=捂脸……
有公开的 id→名称对照表。NapCat 在 `face` 段里有时也直接给了 `summary`。

```
{"type":"face","data":{"id":"182","summary":"[捂脸]"}}  →  "（捂脸）"
```

**这一步就能覆盖大部分日常表情，性价比最高。**

**方案 B：图片自带摘要 + OCR（1 天，零模型成本）**

OneBot 的 `image` 段通常带 `summary`，值形如 `[动画表情]`、`[图片]`。
更关键的是：**大量表情包上带文字**（"你礼貌吗""我裂开了"）。
本地跑个轻量 OCR（RapidOCR / PaddleOCR，CPU 就能跑）把文字抠出来，
往往就足以判断情绪了。

**方案 C：视觉模型描述（1~2 天，有点成本）**

把图片喂给视觉模型，输出"这张图表达了什么情绪/意图"。

- **云端**：Gemini Flash / 通义千问 VL 都支持图片，一次调用几分钱
- **本地**：Qwen2.5-VL-7B 要额外 8~10GB 显存，**和现有的 7B 文本模型冲突**（共 16GB）。
  变通：按需加载（用完卸载）、换更小的 VL 模型、或只在高价值场景调用

**方案 D：表情包库 + 你手动标注（长期，越用越准）**

把收到的表情包按 hash 存下来，第一次遇到时推给你：

```
【新表情包】[图片] 这张什么意思、什么场合用？
  1 = 嘲讽  2 = 撒娇  3 = 无语  4 = 开心  5 = 跳过
```

之后同 hash 直接命中缓存。**零模型成本，准确率最高**，因为是你自己的语义体系。
配合"哪些人爱发哪些表情包"还能学出个人习惯。

**方案 E：让 bot 也会发表情包（反向，效果最好）**

识别只是"读懂"，能**发**才是"像人"。从库里按场合挑一张发出去：

```
对方："哈哈哈"      →  回个笑的表情包
对方：撒娇          →  回个无奈/宠溺的
```

技术上发 `image` 或 `face` 段即可。**"会发表情包"比"能看懂表情包"更能提升人味**，
而且实现比识别简单（只需挑选逻辑，不需理解）。

### 4.3 建议的落地顺序

```
阶段 1  方案 A（face id 映射）           ← ✅ 已完成（399 个官方 id + 自学习）
阶段 2  方案 B（summary + OCR）          ← 部分完成：summary 已用上；OCR 待做
阶段 3  方案 E（会发表情包）             ← 人味提升最大，待做
阶段 4  方案 D（表情包库 + 标注）        ← 越用越准，待做
阶段 5  方案 C（视觉模型）               ← 兜住无字、抽象的图，待做
```

已实现的部分：`face` 段查内置 399 个官方 id 对照表；`mface`/`image`/`record`/
`at`/`reply`/卡片等段类型全部翻译成文字；未知类型也不丢弃（输出 `（[类型名]）`）；
表里没有的表情会用事件自带的 summary 并**写进 SQLite 缓存**，越用越全。

注意阶段 3 比 4/5 更早，因为它提升的是"表现"而非"理解"，性价比更高。
**"会发表情包"比"能看懂表情包"更能提升人味**，而且实现更简单
（只需挑选逻辑，不需理解）。

## 五、如果只挑三件先做

按「效果 ÷ 成本」排序：

1. **拆句发送 + 延迟按字数算**（1.1 + 1.2）
   改动最小，人味提升最直接。现在最大的破绽就在这。

2. ~~长期记忆~~（3.2 ①）—— **✅ 已完成**
   接下来可以补的是"事实的语义检索"（现在只有关键词召回，
   「火锅」搜不到「不能吃辣」，只能靠把偏好类事实always注入来兜）。

3. ~~表情包：face id 映射~~（4.2 A）—— **✅ 已完成**
   下一个该做的是 **4.2 E（让 bot 也会发表情包）**。

再往后是 **安全阀**（3.2 ⑧）——虽然不提升人味，但它控制的是**出错的下限**，
而自动回复这件事，下限比上限重要。

## 六、关于模型选择的实测结论

这次做长期记忆时意外拿到了一个**很有说服力的证据**：

> 同一套提示词、同一份记忆，7B 模型会答出「我准备得差不多了，你呢？」
> 这种视角错乱的句子，也会把无关话题强行扯到记忆上；
> 而在关掉干扰上下文后，它又能正确说出「听说你不太能吃辣」。

也就是说——**制约效果的不是记忆机制，而是模型对复杂指令的遵守能力**。
这正好印证了第二节的判断：

- 记忆、表情这些**机制层**的东西，值得用工程手段做扎实（本次已做）；
- 而**措辞与社交判断**这一层，换一个更大的模型（DeepSeek 官方 API 几块钱/月，
  或国内免费额度的智谱 GLM-4-Flash / 硅基流动）收益会远大于继续调提示词。
